1.redis为什么那么快？
基于内存，命令复杂度低，单线程执行命令主线避免竞争(持久化，异步删会用到后台线程)，网络层采用IO多路复用(一个线程监听多个socket，哪个连接可读写就处理哪个)，其数据结构涵盖多种场景共同作用的结果

2.redis数据类型
5基础+4扩展
String:最常用的场景，可以存json，验证码防过期，接口限流等等
Hash:适合存字段多但修改少的对象，比String整个JSON操作更方便，可以直接修改对象属性
List:理解成有序可重复的链表，两端可操作，如左入右出，保留最近多少条的数据
Set:理解成无序唯一的链表，是否点赞，取交集
ZSet:排序且唯一，排行榜，延迟队列
Bitmap:内存极省，本质还是String,按bit操作。 通常用来做是非及是非统计的操作，如签到
HyperLogLog:近似去重计数，最大占12KB存在误差，用于做海量数据场景下的计数，如月活跃用户数
Geo:存经纬度，常用于距离计算和范围查询
stream:5.0后引入消息队列结构，但一般不用，替代不了专业MQ

3.redis底层编码要点
redis数据类型不是简单的map，同一类型在不同数据规模下编码不同。如hash默认128个字段或64字节以内用listpack，超了切hashtable。生产上可以调大阈值来节省内存

4.redis持久化
redis数据存储在内存里，服务一挂数据就丢失了，有些缓存数据还是不能容忍完全丢失的场景要用到持久化。

两种持久化方式：
	RDB(快照):把内存里的全量数据dump成一个紧凑的二进制文件`dump.rdb`,触发方式通常选用是bgsave(fork 子进程，主进程继续服务)
		优点是文件小恢复快，适合异地容灾。缺点是两次快照间的写操作可能丢失
	AOF(追加日志):把每一条写命令追加到日志文件末尾**（默认 `appendonly.aof`），恢复时重放所有命令。
		AOF rewrite(重写):fork一个子进程，根据当前内存数据重新生成一份最小的命令集，替换掉旧文件。对同一个key只保留最后一条写记录。
		优点是数据更完整，在`everysec`(每秒写)的策略下最多丢一秒的数据；缺点是文件较大，恢复慢
		AOF写入分为两个步骤：1追加到AOF缓冲区 2.刷盘   appendfsync控制的就是刷盘频率，最常用的就是everysec(每秒刷)

fork作用(核心机制是操作系统的cow写时机制)：
	1.主进程接到持久化指令，Linux fork()创建子进程。
	2.子进程拿到父进程内存完整副本。（fork瞬间，子进程其实是和父进程共享同一份物理页，页表标记为只读。当父进程要写某一页时，系统把该页复制一份让父进程去改）
	3.子进程在副本上做快照/重写
	4.主进程继续处理请求，互不影响
cow代价：fork后如果主进程大量写入，被修改的页都要复制。极端情况下内存会接近之前的两倍。因此生产上redis内存利用率不建议超过50%
fork阻塞：如果redis占的内存大，页表也大,fork瞬间主进程会阻塞几毫秒到几十毫秒

RDB 和 AOF rewrite 都依赖 fork + COW，fork 的阻塞和 COW 的内存膨胀是大实例持久化的核心风险，所以生产上一般控制单实例内存，并用 `maxmemory-policy` 和合理的内存预留来兜底。

5.高可用方案
	5.1.主从复制：读扩展(读从库)从库拥有完整数据副本。默认是异步复制，主节点写完内存就返回客户端成功。刚写完主节点不能马上去从节点读(主从延迟)，参考数据库主从复制
	5.2.哨兵模式：在主从复制基础上加上哨兵职责。起码要有一主二从。
		监控：哨兵集群定期Ping主从节点，判断是否存活
		自动转移故障：主节点不可达，哨兵集体投票选出一从节点提升为新主
		通知：故障完成转移后，哨兵通过发布订阅通知客户端新主地址
	5.3.Cluster：数据分片，节点故障转移。该方案解决的是数据分散，而不是单热点数据
		原理：Cluster把所有数据分成16384个哈希槽，每个key相关数据都放在一个槽里，所有的哈希槽由所有主节点平分。
		该方案不支持跨槽的多key操作，解决方案用{}强制让相关key落在同一槽，CRC只对key里{}包括的部分计算，从而落在同一槽
		同理lua脚本涉及的key也必须在同一槽

6.经典问题
	6.1：缓存穿透：查询数据库不存在的数据，直接打到DB
		方案一：缓存设置null
		方案二：若考虑大量null浪费内存，启动时讲所有合法key放入布隆过滤器，查询前先问是否存在。不存在直接返回Null,可能存在就走正常读，该方案有小概率误判
		方案三：参数校验：该方案可直接加上，校验参数是否合法
	6.2.缓存击穿：某热点数据过期，大量请求打到DB
		方案一：互斥锁，第一个获取锁的线程去查DB回填缓存
		方案二：热点数据不设置过期，由后台定时任务刷新
	6.3.缓存雪崩：大批过期热点数据过期，或者redis宕机，导致redis所有请求都打到DB
		方案一：给key设置TTL的时候加个随即抖动，避免同一时刻大量过期
		方案二：本地缓存+redis+db的多层缓存模式
		方案三：限流+redis高可用

	Cache Aside：使用缓存+数据库并存的架构下，我们追求的不是数据绝对一致，而是最终一致。

7.分布式锁
	基本实现：set lock_key UUID NX PX 30000,其中三个要素缺一不可：
	1.NX：key不存在时才设置，保证互斥
	2.PX：设置过期时间，防止死锁
	3.每次加锁用不同的UUID，解锁时校验是不是自己的锁
	通常配合LUA脚本保证比较value+删除key是一个原子操作

	锁续约机制：Redssion框架有watchdog看门狗机制解决这个问题，原理：
	加锁成功后启动一个后台定时任务，每隔ttl/3的时间检查，若活着就把续到之前的TTL;如果持锁线程挂了看门狗也跟着停，锁在TTL到期后释放

	通常来讲Redis做并发所只是做第一层防护(挡住99%的并发，数据库层的乐观锁或排他锁做最终兜底)

8.高级用法和工程实践
	1.LUA脚本
	优点：在redis以原子方式执行，对读判断写的组合很有用，通常用redis分布式锁来挡住大量并发请求
	缺点：脚本会阻塞主线程，通常该脚本要短小精悍，避免在脚本里做复杂运算

	2.Pipeline
	优点：解决的是网络往返次数（RTT）的问题，把多个请求命令打包一次发过去，只需要一次往返
	缺点：并不是原子操作，某条失败不影响其它不回滚

	3.Redis事务MULTI/EXEC
	Redis事务和关系型数据库事务区别很大，Redis事务保证的是命令按顺序执行，执行过程中不会被其他客户端的命令打断，没有回滚，单线程也没有隔离级别

	4.过期策略和淘汰策略
	Redis 用的是惰性删除 + 定期删除的组合：
		惰性删除：访问一个 key 时，检查是否过期，过期就删。不访问就不删。
		定期删除：Redis 每 100ms 随机抽查一批设置了 TTL 的 key，过期的就删。如果过期比例超过 25%，继续再抽查一轮。
	存在的问题，如果某些key过期了也不访问它，也没定期抽到，就会一直占用内存

	淘汰策略：共有八种淘汰策略。通常会根据Redis缓存的数据来选择，如果只做缓存，一般就用allkeys-lur或者allkeys-lfu；如果存了一些不能丢的数据，就用volatile-lru,只对设了TTL的key做淘汰。更安全的做法是把不同重要程度的数据放在不同的redis实例里，做物理隔离

	5.bigKey和hotKey
	5.1.bigKey(一个Hash存了十万字段):网络阻塞，CPU阻塞(redis主线程单线程)，删除慢(生产环境下用UNLINK异步删除)，内存碎片无法利用

	怎么查  redis-cli --bigkeys
	治理方案：大Hash拆分，大的value先gzip压缩再存，异步删除

	5.2.HotKey(高热度):大量请求打到一个redis节点
	怎么查： redis-cli --hotkeys
	治理方案：多级缓存+key分散到不同的节点，热点数据主动加载

9.线上排查
	9.1.Redis阻塞了怎么查？ 是否有慢命令，是否有bigKey，是否执行了keys *,是否内存打满触发淘汰
	9.2.排查常用命令  INFO,SLOWLOG GET,`LATENCY LATEST`
	9.3.内存暴涨? 业务写入变多，是否有过期key一直没有清除，是否是COW导致fork阶段内存膨胀
