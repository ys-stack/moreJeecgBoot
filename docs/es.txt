es
1.es请求一般分为两部分，http方法+路径、JSON请求体
如查询常见结构：
	POST /索引名/_search
	{
	  "from": 0,
	  "size": 20,  //分页
	  "_source": ["返回字段1", "返回字段2"],
	  "query": {
	    "bool": {
              "must": [
                { "match": { "title": "Redis 持久化" } }
              ],
              "filter": [
                { "term": { "status": "ON_SALE" } },
                { "terms": { "brand": ["tech-book", "official"] } },
                { "range": { "price": { "gte": 1000, "lte": 5000 } } }
              ],
              "must_not": [  //排除逻辑
                { "term": { "deleted": true } }
              ],
              "should": [  //命中加分
                { "match": { "tags": "经典" } }
              ]
            }
	  },
	  "sort": [],  //排序
	  "aggs": {}   //聚合统计
	}

我一般把全文检索条件放在 `must`，让它参与 `_score` 打分；把结构化条件放在 `filter`，因为它们只做过滤，不需要打分，还可以利用缓存。这样 DSL 的语义清楚，性能也更好。
常见写结构：
	PUT /product_index
	{
	  "mappings": {
	    "properties": {
	      "id": { "type": "keyword" },
	      "title": {               //后续查询子字段还可以走keyword
	        "type": "text",
	        "analyzer": "ik_max_word",
	        "fields": {
	          "keyword": { "type": "keyword" }
	        }
	      },                     
	      "brand": { "type": "keyword" },
	      "categoryId": { "type": "keyword" },
	      "price": { "type": "integer" },
	      "status": { "type": "keyword" },
	      "createdAt": { "type": "date" }
	    }
  		}
	}
2.常见字段类型，keyword,text,integer/long,date,boolean等
	keyword存整块，适合精确查
	text分词，适合全文搜
3.常见ES查询DSL
	match:全文搜索，先分词。如{ "match": { "title": "Java Redis" } }
	term:精确匹配，不分词，如`{ "term": { "status": "ON_SALE" } }`
	terms:多个精确值匹配，如`{ "terms": { "brand": ["apple", "huawei"] } }`
	range:范围查询，如`{ "range": { "price": { "gte": 1000, "lte": 20000 } } }`
	exists:字段存在，如`{ "exists": { "field": "coverUrl" } }`
	`bool.must`:必须满足，并参与打分
	`bool.must`:必须满足，但不打分可缓存
	`bool.should`:最好满足，可加分
	`bool.must_not`：必须不满足
4.ES和MYSQL的定位：
ES更多的是做全文检索，日志检索分析，更多是作为视图。MYSQL承载核心业务数据，支持事务保证数据强一致。两者之间通过同步链路做最终一致5.核心概念：
	index（索引）:类似数据库中的表，是一类文档的集合，生产环境是被拆成多个分片分布在多个节点上
	Document（文档）：类似数据库中的表一行数据
	Field（字段）
	Shard（分片）:Index的水平拆分，分片是es分布式存储和并行查询的基本单位。
	Replica（副本）：每个主分片可以有0到多个副本，提供高可用和读扩展能力
	Node（节点）
	Cluster（集群）
重点注意shard,一个分片底层就是一个完整的(Lucene)搜索引擎索引，每个由多个Segment（段）组成
每个段更新实质是写入新文档到新的段，再把标记的旧文档删除；多个小的段会被后台合并成大的(Segment 越多，搜索开销越大)

Shard设计：
首要考虑数据分布，查询并行，单分片大小，后续扩展成本四点：
1.数据分布：不同 Shard 可以分布在不同 Node 上，实现水平扩展
2.查询并行：搜索请求会分发到相关的shard上，并行执行后汇总结果
3.单分片大小应在10-50G之间，数量≈ Index 总数据量 / 单个分片目标大小（30GB 左右）。分片多了集群状态更新慢，查询慢，分片本身也有固定的开销，分片少了恢复时间过长，查询并行度不够
4.后续扩展：主分片数一旦创建就不能改（写入时要路由请求，改了路由就变了），所以需要提前规划。

6.倒排索引和分词原理
倒排索引其实就是根据value去找key，即根据内容找文档id。全文检索先在倒排索引找到候选文档ID列表，再做运算，打分，排序等

分词原理就是把文本拆成一个个token词项，存入倒排索引
常见的分词器英文默认分词器，ik中文分词器(分粗细)，生产中需配置同义词，停用词

7.text和keyword的区别
两者都是字段类型，区别在于怎么存，text存拆词后的token，keyword存原样值;
查询keyword适合精准匹配场景，text召回的是分词之后的token到文档的映射；工程上常用多字段映射，让文档标题，正文既能全文检索又能精准匹配
如："title": {
    "type": "text",
    "analyzer": "ik_max_word",
    "fields": {
      "keyword": { "type": "keyword" }
    }
  }

8.match和term区别
两者都是查询方式，term不做分析，直接精确查找；match会先分析输入，拆词去倒排索引查，把命中的文档按相关性打分
通常term配合keyword,match配合text

9.相关性打分
es8默认用BM算法打分，核心思想TF（词频）,IDF（逆文档频率，一个词在索引中越罕见，他在文档中出现的权重越高），文档长度归一化（短篇文档更聚焦）
工程上可以影响打分的手段：给字段加权，自定义打分函数等

10.写入链路与近实时搜索
客户发起请求——协调节点接收——路由计算出shard（根据文档id的hash值计算）——请求转发到目标主分片所在的数据节点——主分片写入（写入内存buffer，同时写入Translog）——
主分片把写入操作转发到所有副本分片——副本分片写入成功后协调节点返回客户端成功相应

es为什么近实时？
refresh机制：写入数据 → 内存 Buffer → [Refresh] → Segment（可搜索）→ [Flush] → 磁盘持久化
Buffer:写入在内存，此时搜索看不到
Refresh:默认每秒执行一次，把buffer中的数据生成一个新的段，放在文件系统缓存，此时就可以搜素
Flush:刷盘，默认30分钟或Translog512M时触发。把文件系统缓存中的段刷到磁盘并清空Translog
所有es的近实时指写入后最多一秒就能查到，不是严格实时；如果系统需要写入立即查，可以手动刷盘POST /product_index/_refresh，这样坏处是会导致段碎片化

常见优化手段：多次写入合并成一次请求（减少网络传输成本）、大批量导入减少refresh频率，副本设为0、routing把相关数据写到同一个分片

11.搜索链路、打分和聚合
es才用两阶段查询模式
客户端发起请求——协调节点接受请求——QUERY阶段——协调节点收集所有分片返回的TopN结果——fetch阶段——返回给客户端
QUERY阶段：协调节点分发查询到相关分片，每个分片在本地查询：对倒排索引做排序、计算相关性打分、按打分排序，返回TopN的文档ID和分数
FETCH阶段：协调节点根据最终文档 ID，到对应分片获取完整文档内容

为什么分为两阶段？
假设有5个分片，Query阶段每个分片返回本地top10的文档ID，5*10=50,Fetch阶段协调节点从50个选出top10，只需获取10个文档的完整内容。直接一步到位网络开销大得多

12.Query和Filter区别：Query打分，Filter只判断是否匹配

13.Mapping设计决定后期成本
    控制字段数量、避免大量使用text、不需要搜索/聚合的字段设index:false,减少倒排索引体积、避免使用浮点型
    nested字段可以解决ES存储JSON文档默认把嵌套对象扁平化的问题，但效率极低，因为每个嵌套对象都是独立文档，设计之初最好避免

14.深分页、排序与性能优化
ES中翻得越深越慢，常用search_after的方式取上一页最后一条文档排序值坐游标，取下一页

排序字段最好是keyword或数值类型，不要对text字段直接排序

常见优化：减少返回字段、Filter代替Query不打分有缓存、控制索引和分片数规模

15.集群模式和分布式架构
常用的节点角色有Master、data、Ingest（写入前预处理）、coordinatingOnly（只做请求路由和结果汇总）
目前用过的架构是 3个master+3个Data+1个运维(kibana,nginx,监控)+2个路由(请求路由，汇总结果)
    注意：
    1.master节点要选奇数，避免平票
    2.当集群出现网络分区可能出现脑裂问题，节点失联各选各的，各自接受写入，导致数据不一致；es7通过法定多数来自动防护，少数派凑不够两票选不出master就拒绝服务。3个节点能接受一个故障，5个能接受两个故障

集群健康状态： green(主分片和副本分片都正常分配)、yellow(主分片正常副的存在未分配)、red(存在主分片未分配)
