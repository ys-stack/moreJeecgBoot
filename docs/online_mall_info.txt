******架构
mall-common 放通用返回、异常、Redis、Swagger配置
mall-security 放 Spring Security、JWT、动态权限过滤器、Redis 配置
mall-admin 接后台用户体系和动态权限
mall-portal 前台商城接口和延迟队列
mall-search：搜索服务，专门接 Elasticsearch
mall-mbg：MyBatis Generator 生成的 Mapper 和 Model

******技术栈
MySQL：核心事务数据，像用户、角色、资源、订单、商品
Redis：缓存和短期状态
MongoDB：浏览记录、收藏这类弱事务数据
Elasticsearch：商品搜索、推荐、聚合导航
RabbitMQ：延迟消息、异步解耦
Spring Security + JWT：认证鉴权
MyBatis + MBG：数据库访问与代码生成

核心架构思想不是“先拆服务”，而是先拆职责。因为一开始直接上微服务成本太高，而模块化单体既能控制复杂度，又能保留后续拆分空间。

******权限设计(spring security过滤器链)
1.首先JWT做认证，查验token正确是否过期；
2.后台动态资源做鉴权，放过白名单(配置文件配置)
3.前台只做登录态控制(匿名和登录两段式)

******缓存设计
1.实现了典型的 Cache-Aside 模式：读时先查缓存，未命中再查库并回填；写时先更新数据库，再删除缓存，由后续读请求懒加载重建缓存。
2.2.实现了 RedisCacheAspect 切面，只有 @CacheException 标注的方法才要求缓存异常向上抛出，避免 Redis 异常影响主业务。
3.对商品等热点场景实现了两级缓存，Caffeine+分布式缓存Redis的方案。本地缓存从JVM内存读取延迟更低更稳定，在热点数据非常集中的场景能显著减少redis的压力； 查询顺序 本地缓存->分布式缓存->DB
4.本地缓存通常存读多写少、热点集中、响应要求不高、序列化成本低的数据(商品信息，树，字典等)
5.L1 的 TTL 通常短于 L2，并加入随机抖动，缩小本地缓存不一致窗口，避免批量过期
6.Redis 层支持空值缓存，防止缓存穿透
7.高并发场景下，使用 Redis 分布式锁进行互斥重建，避免缓存击穿时大量请求直接打到数据库

--更新缓存都是删除新增，避免更新链路过长造成一致性问题

	--场景1：查询商品详情 product:1001
	1.请求先到应用节点 A
	2.先查本地 Caffeine，命中则直接返回，未命中则查 Redis
	3.Redis 命中则返回结果，并回填本机 Caffeine ，Redis 未命中则查 DB
	4.DB 查到后写入 Redis，设置较长 TTL 和随机抖动；再写入本机 Caffeine，设置较短 TTL 和随机抖动
	5.返回结果

	--这里的关键点是：  
	L1 ：TTL 通常比 L2 TTL 更短(L1本地缓存最容易出现“各节点不一致”问题，所以它不能活太久，根据业务对脏读的容忍度去定义TTL时间,TTL加随机抖动防止批量过期)
	L2 ：用 Redis，长 TTL，也带抖动
		 db中数据不存在时写入空值缓存，避免缓存穿透
		 高并发场景下用redis分布式锁做了互斥重建，先用redis setIfAbsent抢锁，抢不到就进入等待状态等待其他线程回填，这样可以避免一波请求都打到DB

	--按业务类型可以这样粗分：
	商品详情、类目、品牌这类“读多写少”数据：L1 30~120 秒，L2 30~120 分钟
	价格、营销文案这种改动相对频繁的数据：L1 5~30 秒，L2 5~30 分钟
	库存、余额、秒杀状态这类一致性要求高的数据：L1 要么不用，要么 1~5 秒甚至不走本地缓存

	--场景2：写的时候保证缓存的一致性(广播+TTL)
	1.先更新数据库
	2.在同一个事务内写入两条缓存失效 outbox 记录，第二条带延迟
	3.事务提交成功后，在 afterCommit 回调中立即尝试投递失效消息
	4.投递前先删除 Redis 中对应商品详情缓存
	5.通过 RabbitMQ fanout exchange 将失效消息广播给所有 portal 实例
	6.每个 portal 实例都有自己的持久化队列，消费成功后手动 ACK，并删除本机 Caffeine；若消费不成功放至死信队列，后续人工处理   至此缓存算清空
	7.调度器定时扫出：同时写入一条延迟双删 outbox 消息，约 500ms 后再次删除 Redis 并再次广播 逻辑和之前的投递一样
	8.若应用在事务提交后宕机，调度器会扫描 outbox 表并补发消息
	9.若消息处于 processing 状态超时未完成，也会被重新纳入补发流程
	10.若消费者处理失败，消息进入死信队列，避免静默丢失
	11.TTL 作为最终兜底，保证极端情况下本地脏数据不会长期存在

	这一套方案的核心不是强一致，而是高可靠的最终一致性。把消息丢失和缓存不一致风险降到可控范围。

	亮点：
	1.本地缓存采用显式TTL+访问时过期判断的方式失效；加了outbox表延迟双删，一是避免脏数据影响业务，二是防止环境异常导致消息丢失，造成业务异常
	2.缓存方案主要是针对商品等热点数据，级缓存、空值缓存、分布式锁、MQ 广播失效、outbox
	3.outbox和业务提交公用一个事务，但投递缓存失效要等到事务提交完成后再投递(注册提交后事件)，如果提交后宕机不影响补发
	4.本地缓存自己维护过期时间，定义不同的过期时间常量写在配置里根据热点信息数据系统分配；添加缓存的时候加随机抖动，防止批量过期
	5.高并发场景下，加了分布式锁，其中锁释放是lua校验后删除value，不是裸删；且没抢到锁的自旋等待其余线程回填，避免大量请求都打到DB

******商品业务
核心主线：商品浏览--购物车--促销计算--优惠券筛选--下单--支付--订单关闭/确认收货

商品(商品详情是前台流量入口，同时又是一个聚合查询接口，它天然适合做热点缓存优化)：
	前台的商品详情不止是查一张表，需要多张表构建成一个完整详情对象，大致包含商品基础信息，品牌信息，商品属性，属性值，sku列表，价格阶梯，满减信息，可用优惠券
	注：sku指一个最小库存单元，如"iphone15,12G,128G,黑色,国产,库存100"这就是一个sku，即商品的某个具体版本
购物车(不只是存商品，而是为后续营销计算准备上下文)
	1.商品id+skuId+会员Id合并，这是重复加购增加数量的前提，标准电商购物车模型
	2.购物车不光是展示sku的列表，而是订单确认前的计算入口，提前会将原始购物车交给促销服务再返回带促销结果的购物车
促销业务：
	1.计算每个购物车项价格，优惠金额，赠送积分，库存等，根据促销类型(满减，阶梯折等)
	这个项目里的促销不是单独一个大营销引擎，而是嵌在购物车和订单流程里的商品级促销计算模块，重点解决实时算价和活动命中问题
优惠券业务：
	1.领券（检查优惠券是否还在，剩余数量，领取次数超限，领取资格，留痕记录等）
	2.检查自己的券种类
	3.查询当前商品的可用券
	4.最关键的是在购物车判断哪些券能用，优先用
	优惠券业务不是独立存在的，而是和购物车促销联动，先算商品促销，再判断哪些券在当前购物车上下文中可用
订单业务：
	1.确认订单
		1.1.获取选中的购物车项
		1.2.获取收货地址
		1.3.获取当前购物车可用优惠券
		1.4.获取用户积分
		1.5.获取积分使用规则
		1.6.计算商品总额
		1.7.活动优惠
		1.8.应付金额
	2.正式下单
		2.1.检验收货地址
		2.2.取出购物车和促销结果
		2.3.构造订单项
		2.4.校验库存
		2.5.处理优惠券分摊
		2.6.处理积分抵扣
		2.7.计算订单项实付金额
		2.8.锁定库存
		2.9.组装订单主表
		2.10.插入订单和订单项
		2.11.更新优惠券状态
		2.12.扣积分
		2.13.删除已下单的购物车项
		2.14.发生延迟取消订单消息
