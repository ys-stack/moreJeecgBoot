    1.4.缓存设计与系统调优：
        **怎么实现增效降本：
        ****需解决的问题：相同文本重复上传，重新解析或重新同步时，每次都调用 Embedding Api，会增加费用和处理时间；
              高频FAQ问答，相同用户问题反复执行 Embedding、ES 检索、Rerank 和大模型生成，会消耗大量外部资源
        ****架构： Embedding向量缓存，读取链路
                    Caffeine 本地缓存
                            ↓ 未命中
                    Redis 二进制缓存
                            ↓ 未命中
                    MySQL ai_embedding_cache
                            ↓ 未命中
                    硅基流动 Embedding API

                  RAG FAQ答案缓存，读取链路 （答案缓存只用于第一轮、无历史上下文的独立问题，避免上下文语义不同）
                    权限范围和知识库版本计算
                            ↓
                    Caffeine 本地答案缓存
                            ↓ 未命中
                    Redis 加密答案缓存
                            ↓ 未命中
                    Embedding → ES → Rerank → LLM
        ****细节1：为了应对AI切片向量1024维直接用JSON序列化放入redis造成JSON膨胀(一条就要超过12K)。单独配置了定制化 RedisTemplate，
将float[]压缩成原生二进制byte[]存储，单条切片空间被压至4k。此举大大精简了redis内存占用和网络传输消耗，也消除了JSON反序列化对CPU的消耗
        ****细节2：缓存击穿处理，遇到多个节点同时访问同一个未缓存的文本时，使用分布式锁避免同时多次调用embedding api，获取到锁的请求负责回填缓存。
未获得锁的请求短时间轮询缓存，等待超时后降级调用api避免阻塞
        ****细节3：数据安全设计：租户隔离/缓存建加密（HMAC-SHA256）/答案加密（可能存在敏感信息）
