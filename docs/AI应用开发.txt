# AI 应用开发项目总结（面试强化版）

## 一、项目定位

我基于 JeecgBoot/Spring Boot 搭建了一套企业级 AI 应用实践平台，不只是调用大模型 API，而是围绕模型接入、Prompt 工程、RAG、Tool Calling、Agent、缓存、权限、安全、评测、成本和稳定性做完整工程治理。

项目目前包含两条核心业务链路：

1. RAG 企业知识库：文档上传与解析、语义切分、Embedding、Elasticsearch 向量检索、Rerank 精排、权限过滤、查询改写、多轮会话、引用来源和低相关度拒答。
2. Tool Calling Agent：数据库动态工具定义、JSON Schema 参数约束、角色权限过滤、业务 Handler 执行、写操作确认、审计日志、最多 5 轮推理循环以及 SSE 过程事件。

项目的技术主线可以概括为：

```text
模型能力接入
  -> Prompt 和结构化输出
  -> RAG 外部知识增强
  -> Tool Calling 连接业务系统
  -> Agent 多步编排
  -> 缓存、权限、评测、成本和稳定性治理
```

---

## 二、已完成的核心功能

### 1. 模型接入与调用治理

- 使用 LangChain4j 对接 OpenAI 兼容协议模型，支持同步对话、SSE 流式输出和结构化 JSON 输出。
- 模型、API 地址、API Key、温度、最大 Token 和超时全部配置化，敏感信息通过环境变量或本地私有配置注入。
- 使用自定义 `@ModelInvocationLog` + AOP 记录调用场景、模型、用户、Token、耗时、状态和异常，为成本统计、问题排查和模型切换提供数据基础。
- 使用 `@RateLimit` + Redis Lua 实现原子限流，避免“先读后写”在并发下超卖限额。
- 流式任务、普通异步任务使用独立线程池，避免 SSE 长连接长期占用通用业务线程，并支持线程池监控和优雅停机。

技术理解：模型 API 本质上是不稳定且有成本的外部服务，必须像治理支付、短信等外部依赖一样处理超时、限流、审计、重试、隔离和降级。

### 2. Prompt 工程

- Prompt 模板存储在 MySQL，支持 `promptCode`、场景、版本、启停状态和变量渲染。
- 业务代码不硬编码 Prompt，通过模板编码获取当前激活版本，方便灰度、回滚和多场景复用。
- 高频模板使用 Caffeine 本地缓存，减少每次模型请求都访问数据库的开销。
- 结构化输出不仅要求模型“返回 JSON”，还需要反序列化校验、必填字段检查和失败处理。
- 模型调用日志记录 Prompt/模型版本，使线上回答能够追溯到具体配置。

面试重点：Prompt 应被当作一种可版本化、可测试、可回滚的业务配置，而不是散落在代码里的字符串。

### 3. 文档解析与知识库建模

- 知识库、文档、文档分片分别建模，保留文档状态、来源、分片序号、标题路径和知识库关联。
- Python FastAPI 文档解析服务支持 Markdown、TXT、PDF、DOCX，Java 负责业务事务、权限、存储和后续向量化。
- 文档切分优先保持标题和段落语义边界，超长内容再二次切分，而不是单纯每 N 个字符硬切。
- 每个 chunk 保留 `documentId`、`knowledgeBaseId`、标题、来源文件、chunkIndex 等 metadata，用于引用展示、权限过滤、删除和问题排查。

切分策略的取舍：

- chunk 太小：上下文不完整，同一事实可能被切散。
- chunk 太大：向量语义被稀释，召回噪声增加，同时消耗更多上下文 Token。
- overlap 太大：重复召回和存储成本上升。
- 最合理的方案不是固定参数，而是根据文档类型和评测结果调整。

### 4. Embedding 生成与三级缓存

- 使用硅基流动 bge-m3 生成 1024 维向量。
- Embedding 是确定性较强、成本较高、网络 IO 较慢的计算，适合按标准化文本结果复用。
- 实现 Caffeine + Redis + MySQL 三级缓存：

```text
L0 Caffeine：单实例内存命中，延迟最低
L1 Redis：多实例共享，减少跨节点重复计算
L2 MySQL：长期持久化，Redis 丢失后仍能恢复
缓存未命中：调用 Embedding API，再逐级回填
```

- 缓存键不是只对原文本做 MD5，而是包含租户、模型名、模型版本、归一化版本、向量维度和规范化文本摘要，避免模型升级或维度变化后复用错误向量。
- 并发未命中时使用 Redis 分布式锁控制单个请求计算，其他请求短暂等待缓存回填，降低缓存击穿和重复调用模型的成本。
- 解锁使用 Lua 校验锁 Token，避免线程 A 的锁过期后误删线程 B 新获得的锁。
- 向量序列化采用二进制编码并做防御性复制，避免直接缓存可变数组造成数据污染。

面试表达：三级缓存不是越多越好，主要是对延迟、共享能力和持久性的分层。Caffeine 解决本机热数据，Redis 解决多节点共享，MySQL 解决持久恢复。

### 5. Elasticsearch 向量存储与检索

- 使用 Elasticsearch 8.x 的 `dense_vector`、cosine similarity 和 HNSW 索引存储 chunk 向量。
- 使用原生 REST API + `RestTemplate` 管理索引、`_bulk` 批量写入、kNN 检索、计数和 `_delete_by_query`，没有使用 JPA，也没有强绑定 ES Java Client。
- Bulk 请求使用 `application/x-ndjson`，逐条检查 `items` 中的状态；只要存在部分失败，就让整个同步任务进入重试，避免 MySQL 显示成功但 ES 缺少部分分片。
- `document_id`、`knowledge_base_id` 使用 keyword mapping，过滤和删除使用 `term/terms` 精确查询。
- 写 ES 前使用 Semaphore 限制物理写并发，防止批量任务同时打满 ES HTTP 连接或触发 429。

为什么直接使用 REST API：

- 优点：请求结构透明、版本行为可控、依赖较轻，便于理解 ES DSL 和 Bulk 返回语义。
- 缺点：需要手写 JSON、错误解析和版本兼容；复杂度继续增加时应评估官方 Java Client。

### 6. RAG 检索与生成链路

完整 RAG 流程：

```text
校验用户和会话归属
  -> 计算当前用户可访问的知识库集合
  -> 首轮 FAQ 尝试答案缓存
  -> 多轮问题结合会话摘要和历史消息做 Query Rewriting
  -> 对查询生成 Embedding
  -> ES kNN 召回 topK * 4 候选
  -> bge-reranker-v2-m3 Cross-Encoder 精排 topK
  -> 过滤低于阈值的结果
  -> 将 chunk、来源和历史消息构造成 Grounded Prompt
  -> 调用大模型生成回答
  -> 保存用户消息、AI 消息、引用和会话摘要
```

关键设计：

1. Query Rewriting：多轮对话中“它怎么配置”这类问题缺少独立语义，结合历史摘要改写为可检索问题，但首轮独立问题不需要改写。
2. 粗排 + 精排：向量 kNN 适合高效召回，Reranker 使用 Cross-Encoder 联合编码 query 和 document，计算更贵但排序更准确，因此只处理候选集，不能替代召回层。
3. 低相关度拒答：Rerank 分数低于阈值时不让模型自由发挥，直接返回知识库未找到依据。
4. 引用来源：回答保存本次检索 chunk 的文档名、标题、chunkId 和分数，方便用户核验，也方便评测引用命中率。
5. 权限前置：先计算用户可访问知识库，再将知识库 ID 和租户作为 ES filter；没有权限时应返回空结果，而不能退化为搜索全部。
6. 会话归属：读取 session 和历史消息时同时校验 userId，防止通过猜测 sessionId 读取他人会话。

当前已实现纯向量召回 + Rerank；BM25 + kNN + RRF 混合检索仍属于下一阶段，面试时不能说已经完成。

### 7. RAG 答案两级缓存与多节点失效

- 高频 FAQ 使用 Caffeine + Redis 两级答案缓存，只缓存首轮、独立、上下文无关的问题，避免错误复用依赖历史对话的回答。
- 缓存键包含租户、权限知识库集合、知识库版本指纹、模型版本、Prompt 版本和规范化问题。
- 不能只用“问题文本”做缓存键，否则不同租户、权限或知识版本可能读到彼此的回答，形成数据泄露或旧答案问题。
- 知识库内容变化后提升版本号，新请求自然生成新 Key，旧缓存即使尚未物理删除也不会继续命中。
- 使用 ActiveMQ Virtual Topic 广播缓存失效消息，每个应用实例通过独立队列清理本节点 Caffeine，解决本地缓存多节点一致性问题。
- 通过 Micrometer 记录 Caffeine/Redis 命中、未命中等指标，为判断缓存是否真正有效提供数据。

### 8. MySQL 到 Elasticsearch 异步一致性

- 文档和分片以 MySQL 为事实源，ES 是可重建的检索副本。
- 文档写入、分片写入、文档完成状态和 Outbox 任务在同一个数据库事务提交。
- 事务提交后向 ActiveMQ 发送任务；如果 MQ 发送失败，Outbox 中的任务仍然存在，定时任务可以补偿。
- MQ 消息携带独立 `taskId`，消费者只完成当前任务，避免旧消息错误完成后续任务。

Outbox 状态机：

```text
PENDING     业务事务已提交，等待发送
PROCESSING  被某个调度实例通过条件更新抢占
DISPATCHED  已发送 MQ，等待消费者确认
SUCCESS     ES 同步成功
FAILED      本次发送或消费失败，等待重试
DEAD        达到最大投递次数，等待人工处理
```

可靠性措施：

- MQ 生产者不吞异常，发送失败必须让 Outbox 感知。
- 多实例调度通过 `id + 原状态 + retryCount` 条件更新抢占，只有一个实例能成功。
- PROCESSING/DISPATCHED 超时未确认会重新投递。
- ES INDEX 使用固定 chunkId，DELETE 本身幂等，允许至少一次投递产生的重复消费。
- INDEX 写入前后再次检查 MySQL 文档，防止 DELETE 先执行、旧 INDEX 后到达导致 ES 数据“复活”。
- 成功任务按保留时间清理，超过最大重试次数进入 DEAD，避免无限重试和表无限增长。

面试重点：Transactional Outbox 解决的是“本地事务已经成功，但 MQ 消息没有可靠发出”的双写一致性问题；它提供最终一致性，不是分布式强一致。

### 9. 熔断、超时和故障隔离

- 使用自定义 `@CircuitBreaker` + AOP + `LocalCircuitBreaker` 实现 CLOSED、OPEN、HALF_OPEN 状态机。
- 连续失败达到阈值后进入 OPEN，后续请求在应用内快速失败，不再继续压迫 ES。
- 冷却期后进入 HALF_OPEN，同一时间只允许一个探测请求；连续探测成功后关闭熔断，任意失败重新打开。
- IllegalArgumentException 等配置的忽略异常不计入熔断，避免业务参数错误污染下游健康判断。
- 熔断器不负责终止已经开始的请求，真实调用仍依赖 RestTemplate 的 connectTimeout/readTimeout。

需要明确的边界：当前是单机内存熔断器，适合练习状态机和 AOP 原理；更复杂的生产系统可替换 Resilience4j，获得滑动窗口失败率、慢调用比例、Micrometer 指标和动态配置。

### 10. Tool Calling 与 Agent

- 工具定义存入数据库，包含 toolCode、描述、JSON Schema、handlerRef、工具类别和是否需要确认。
- 启动/调用时将 JSON Schema 转成 LangChain4j ToolSpecification，模型返回 ToolExecutionRequest 后，由服务端查找对应 Spring Handler 执行。
- Handler 使用策略模式扩展；抽象基类用模板方法固定“解析参数 -> 校验 -> 权限上下文 -> 执行业务”的流程。
- 参数校验使用白名单思维：必填、长度、格式、枚举和注入特征检查，不能直接信任模型生成的参数。
- 工具列表在发送给模型之前按角色过滤；无权限工具不进入 Prompt，比“模型调用后再拒绝”更安全也更省 Token。
- 使用 ThreadLocal 向 Handler 传递当前用户、sessionId 和 messageId，并在 finally 中清理，防止线程池复用造成用户上下文串线。
- 查询类工具直接执行；写工具需要用户确认；所有工具调用记录输入、输出、耗时、用户和状态。
- Agent 显式循环最多 5 轮：模型请求工具 -> 执行 -> ToolExecutionResultMessage 回填 -> 再次调用模型，直到得到文本答案或达到终止条件。
- SSE 输出 thinking、tool_call、tool_result、confirm、message、done/error 等事件，让前端可以展示执行过程。

当前确认流程仍有进一步工程化空间：生产环境应由服务端保存“用户 + 工具 + 完整参数 + 过期时间”的确认单，用户确认具体操作内容，而不是只确认工具名称。

### 11. 评测体系

- 建立 RAG/Agent 评测数据集、执行结果和评测报告模型。
- RAG 评测包含回答关键词相关性、引用命中和应拒答场景得分。
- Agent 评测包含工具选择、参数准确性和任务完成度。
- 单条用例计算总分和是否通过，报告统计通过率、平均分以及各子指标。
- 支持基线版本和目标版本对比，输出通过率、平均分和引用命中率等变化。

面试重点：AI 功能不能只靠“我试了几个问题感觉不错”。Prompt、模型、切分、topK、阈值和 Reranker 的修改都应该通过固定评测集对比，否则无法知道提升来自哪里，也无法阻止回归。

## 三、关键技术问题与面试回答

### 1. 为什么 RAG 不能简单理解成“把文档发给大模型”？

完整文档通常超过上下文窗口，全部发送成本高、噪声大，而且存在权限问题。RAG 的核心是先用检索缩小知识范围，只把和问题相关且用户有权限的数据交给模型，并保留引用证据。

### 2. Embedding、向量检索和 Reranker 有什么区别？

- Embedding：把文本映射为向量，用于衡量语义距离。
- 向量检索：在大量向量中快速找近邻，重点是召回效率。
- Reranker：同时阅读 query 和候选文档，重新计算相关性，重点是排序精度。

Reranker 计算成本高，所以一般采用“向量召回 top20，再精排 top5”，而不是对全库逐条打分。

### 3. 为什么不把 topK 调得越大越好？

topK 过小可能漏召回，过大会把不相关内容送入 Prompt，增加 Token、延迟和模型被噪声带偏的概率。合理的 topK 应通过 Recall、引用命中率、回答准确率和延迟共同确定。

### 4. 如何判断 RAG 回答错误发生在哪一层？

按链路分层排查：

1. 文档解析是否丢内容。
2. chunk 是否切断关键语义。
3. Embedding 模型和维度是否一致。
4. ES 是否召回正确 chunk。
5. Reranker 是否把正确结果排到前面。
6. 阈值是否误过滤。
7. Prompt 是否明确要求只依据上下文。
8. 模型是否忽略资料或生成虚假引用。

不要一看到答案错就只改 Prompt。

### 5. 为什么缓存键必须包含权限范围？

AI 答案本身可能包含知识库内容。如果 A 用户和 B 用户问题相同但权限不同，只按问题缓存会让 B 读到 A 有权访问的答案。缓存键必须绑定租户、知识库权限集合和知识版本，缓存也是权限边界的一部分。

### 6. 如何解决缓存击穿、穿透和雪崩？

- 击穿：热点 Key 失效后大量请求同时调用模型，使用分布式锁和短暂等待回填。
- 穿透：无效请求反复查不到，可做输入校验、空值短缓存和限流，但不能长期缓存错误拒答。
- 雪崩：大量 Key 同时过期，可使用分散 TTL、分层缓存、限流和下游熔断。

### 7. Redis 挂了系统应该 fail-open 还是 fail-close？

取决于功能：

- 普通接口限流：可以暂时 fail-open，保证可用性，但要告警并依赖网关兜底。
- 权限控制：必须 fail-close，不能因为 Redis/权限服务异常就放开全部数据。
- 缓存：缓存异常应回源，但要防止回源流量压垮数据库或模型服务。

### 8. MySQL 和 ES 为什么不用双写？

直接双写存在两个不可原子的问题：MySQL 成功、ES 失败；或者 ES 成功、MySQL 回滚。项目使用 MySQL 作为事实源，通过本地 Outbox + MQ 异步构建 ES 副本，失败可重试、任务可审计、ES 可重建。

### 9. 重复 MQ 消息如何处理？

采用至少一次投递语义，并让消费操作幂等：INDEX 的 ES `_id` 使用固定 chunkId，重复写是覆盖；DELETE 重复执行结果仍正确；Outbox 使用 taskId 精确确认，避免旧消息完成新任务。

### 10. Tool Calling 和普通接口编排有什么区别？

普通编排的流程由程序员预先确定；Tool Calling 由模型根据自然语言和工具描述决定调用什么工具及参数。模型只拥有“申请调用”的能力，真正执行、鉴权、校验、确认和审计全部由后端控制。

### 11. 为什么工具权限要在模型看到工具之前过滤？

如果无权限工具仍进入 Prompt，模型可能不断尝试调用，既浪费 Token，也扩大提示注入和越权攻击面。前置过滤后模型根本不知道该工具存在，Handler 内再做数据级权限形成纵深防御。

### 12. Agent 为什么必须有最大轮数？

模型可能在“调用工具 -> 不满意 -> 再调用”之间循环。最大轮数是资源和安全边界，还应该配合总 Token、总耗时、重复工具调用检测和用户取消。

### 13. SSE 为什么需要独立线程池？

SSE 是长连接，生命周期远长于普通 HTTP 请求。如果和普通异步任务共用线程池，大量慢客户端会占满线程，影响日志、文档处理等任务。独立线程池可以分别设置容量、队列和拒绝策略，并单独监控活跃线程与连接数。

### 14. 熔断和重试有什么区别？

- 重试解决偶发失败，但会放大持续故障流量，只适合幂等操作并需要退避。
- 熔断解决持续失败，达到阈值后快速失败，保护线程和下游。
- 超时负责结束单次调用，隔离负责限制故障影响范围。

工程上通常是：超时在最内层，有限重试在中间，熔断在外层，并配合并发限制。

### 15. 如何评估 AI 应用成本？

至少记录输入 Token、输出 Token、Embedding 次数、Reranker 次数、平均上下文长度、缓存命中率和失败重试次数。日成本可按：

```text
对话成本 = 输入 Token × 输入单价 + 输出 Token × 输出单价
检索成本 = Embedding 调用 + Reranker 调用 + ES/Redis/数据库资源
总成本还要考虑缓存未命中和失败重试带来的放大
```

| 问题 | 当前选择 | 原因 | 边界/后续 |
| --- | --- | --- | --- |
| AI 框架 | LangChain4j | Tool Calling API 较底层，方便手动控制 Agent 循环 | 框架不是重点，协议理解可以迁移到 Spring AI |
| 向量存储 | Elasticsearch 8.x | 已有 ES 能力，支持向量、过滤和全文检索 | 数据规模和检索需求扩大后再评估专用向量库 |
| ES 客户端 | RestTemplate + REST DSL | 请求透明、版本可控 | JSON 和错误处理成本较高 |
| 文档解析 | Python FastAPI | PDF/DOCX 生态成熟 | 需要健康检查、超时、部署和接口版本治理 |
| Embedding 缓存 | Caffeine + Redis + MySQL | 兼顾延迟、多节点共享和持久化 | 需要监控命中率，避免缓存层级过度复杂 |
| RAG 答案缓存 | Caffeine + Redis | FAQ 命中延迟低 | 仅缓存首轮独立问题，缓存键必须包含权限和知识版本 |
| MySQL-ES 同步 | Outbox + ActiveMQ | 避免数据库与 MQ/ES 双写丢失 | 最终一致，需要 DEAD 告警和人工补偿入口 |
| 限流 | Redis Lua | 原子、适合多节点 | Redis 故障策略要按业务风险选择 |
| 熔断 | 自定义 AOP 状态机 | 理解原理、满足练习项目 | 生产复杂场景建议 Resilience4j |
| Agent 控制 | 显式最多 5 轮循环 | 中间状态和 SSE 事件完全可控 | 还应补总耗时、Token 预算和重复调用检测 |

## 五、面试项目介绍话术

### 30 秒版本

我基于 JeecgBoot 做了一套企业 AI 应用平台，核心包括 RAG 知识库和 Tool Calling Agent。文档由 Python 服务解析，Java 做语义切分，使用 bge-m3 生成向量并写入 Elasticsearch，查询时先 kNN 召回再用 Reranker 精排，带租户和知识库权限过滤，回答保存引用来源。Agent 的工具定义和 JSON Schema 存数据库，模型只负责申请调用，后端负责参数校验、权限、确认、执行和审计。工程上还做了 Prompt 版本、Embedding 三级缓存、答案两级缓存、Redis Lua 限流、SSE 线程池、MySQL-Outbox-MQ-ES 最终一致性、熔断以及 RAG/Agent 评测。

### 2 分钟版本

这个项目不是单纯接一个聊天接口，而是研究如何把大模型安全地接入企业后端。

第一条主线是 RAG。用户上传 PDF、Word 或 Markdown 后，由 Python FastAPI 负责解析，Java 根据标题和段落语义切分，保留文档来源、标题路径和权限 metadata。Embedding 使用 bge-m3，并做 Caffeine、Redis、MySQL 三级缓存和分布式锁，减少重复模型调用。向量写入 ES 8.x dense_vector 索引，查询时先 kNN 召回 topK 的多倍候选，再用 Cross-Encoder Reranker 精排，低相关度直接拒答。多轮对话会结合历史摘要做 Query Rewriting，检索前先计算用户可访问的知识库，回答带引用来源。

第二条主线是 Tool Calling Agent。工具定义、描述和 JSON Schema 存数据库，通过 handlerRef 绑定 Spring Handler。模型返回工具调用请求后，后端先做角色过滤、参数白名单校验和数据权限，再执行业务。写操作需要用户确认，所有工具调用有审计日志。Agent 最多执行 5 轮，并通过 SSE 输出思考、工具调用、工具结果和最终回答。

工程治理方面，模型调用通过 AOP 记录 Token、耗时和成本；Redis Lua 做多节点限流；流式和异步任务使用独立线程池；MySQL 到 ES 使用 Transactional Outbox + ActiveMQ 做最终一致性；ES 持续失败时使用熔断器快速失败；最后用固定数据集评测 RAG 的回答相关性、引用命中、拒答能力，以及 Agent 的工具选择、参数准确率和任务完成度。

## 六、可以重点讲的三个技术难点

### 难点一：MySQL、MQ、ES 三者的一致性

最初如果直接在业务代码中“先写 MySQL，再发 MQ”，应用可能在两步之间宕机，导致数据已提交但 ES 永远不同步。最终使用本地 Outbox，把业务数据和同步任务放入同一事务。任务发送失败由定时器扫描补偿，多实例通过条件更新抢占，消费者按 taskId 确认，INDEX/DELETE 做幂等并处理乱序。这体现的是分布式系统中的最终一致性和可恢复性，而不是只会调 MQ API。

### 难点二：缓存既要提速，也不能突破权限

Embedding 适合跨请求复用，但模型版本、维度、文本归一化变化都会影响结果，因此缓存键需要带版本信息。RAG 答案更敏感，必须加入租户、权限知识库集合和知识版本；否则同一个问题可能造成跨租户数据泄露。多节点本地缓存通过 Virtual Topic 广播失效，说明缓存一致性不能只考虑 Redis，还要考虑每个 JVM 的本地状态。

### 难点三：Agent 的安全边界

模型输出不可直接信任。项目把工具权限过滤放在模型看到工具之前，Handler 再做参数白名单和数据级权限；ThreadLocal 必须 finally 清理；写操作需要确认；Agent 有最大轮数。核心原则是模型只能提出建议和调用申请，最终权限与执行权始终在确定性后端代码中。

## 七、目前的不足和下一步优化

面试时主动讲边界比夸大功能更可信：

1. 当前检索是向量召回 + Rerank，尚未完成 BM25 + kNN + RRF 混合检索；下一步先用评测集建立纯向量基线，再增加 BM25 验证专有名词召回是否提升。
2. 自定义熔断器适合学习原理，但缺少滑动窗口失败率、慢调用比例和完整指标；生产环境建议迁移 Resilience4j。
3. Agent 写操作确认需要升级为服务端确认单，绑定用户、工具、完整参数摘要和过期时间，防止确认内容与实际执行内容不一致。
4. 需要补充真实 MySQL、ActiveMQ、ES 故障注入测试，包括 MQ 不可用、ES 部分 Bulk 失败、重复消息、乱序消息和应用宕机恢复。
5. 评测目前以规则评分为主，可以增加人工标注、LLM-as-Judge 一致性校验，但 Judge 本身也需要基线和抽检。
6. 应补容量数据：P95/P99 延迟、并发 SSE 数、缓存命中率、ES 索引规模、单次问答 Token 和日成本。
7. Prompt 注入防护仍要持续加强，包括上下文与用户指令分区、敏感工具隔离、输出脱敏和越权评测用例。
